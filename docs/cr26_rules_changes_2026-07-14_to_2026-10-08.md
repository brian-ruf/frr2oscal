# FedRAMP CR26 Rules: Changes from July 14 to October 8, 2026

## Scope and method

- **Source:** `fedramp-consolidated-rules.json` in `github.com/FedRAMP/rules`, compared commit by commit.
- **Baseline:** commit `083137d`, version `2026.07.14.01`. This is the last state used in the analysis earlier in this conversation.
- **Latest:** commit `6eb3767`, version `2026.10.08.01`.
- **Method:** a structural (field-level) diff of the JSON between each pair of consecutive releases, not a text diff. Where a change is described as "terms list only" or "typo," I confirmed that no `statement`, `name`, `following_information`, or `force` value changed in the affected entries.
- **Not covered:** the JSON Schemas for the CPO, SDR, and vulnerability reports are hosted on fedramp.gov and are not in this repo. Whether they changed with these releases is unchecked. The commits also reference GitHub issues (#30 to #35 and #38 to #39) that I did not read. The "why" below comes only from each rule's own `updated` comment.

## Release 2: 2026.09.13.02 (PR #29, "added force definitions")

**Five new glossary definitions: the force terms**

Each applies "only when the term is used in all capital letters in FedRAMP materials."

| ID | Term | Definition (condensed) |
|---|---|---|
| `FRD-MST` | MUST | Absolute requirement. Parties MUST meet it and address it in their security documentation. Failure to follow it "is a vulnerability likely requiring corrective action and/or the denial of initial or ongoing FedRAMP Certification." |
| `FRD-MNT` | MUST NOT | Absolute prohibition, with the same consequence as MUST. |
| `FRD-SHD` | SHOULD | There may be valid reasons to ignore the rule, but the implications must be carefully weighed. Parties **MUST address such rules in their security documentation by explaining their decisions**. |
| `FRD-SNT` | SHOULD NOT | Same pattern as SHOULD. |
| `FRD-MAY` | MAY | Truly optional. Parties SHOULD address it by explaining their decisions. |

All five are flagged `do_not_link` and `ignore_in_terms`, so they are never auto-listed as cross-referenced terms.

**Why this matters for security documentation:** these definitions put a documentation expectation on rules that are not MUSTs. A provider that does not follow a SHOULD rule is expected to explain that decision in its security documentation. The rules do not say where in the SDR that explanation goes.

**Terms lists pruned**

- Four existing definitions (`FRD-ADV` Advisor, `FRD-AGY` Agency, `FRD-ASR` Assessor, `FRD-PRV` Provider) were flagged `ignore_in_terms`.
- As a result, the `terms` cross-reference lists changed on **236 of 246 FRR rules** and on 6 KSIs. "Provider" was removed from 192 rules, "Agency" from 57, "Assessor" from 36, and "Advisor" from 3. Nothing was added.
- **No rule statement, name, item list, note, or force value changed in this release.** All 236 changes are cross-reference bookkeeping.

## Release 4: 2026.10.08.01 (PR #40)

**`SDR-CSX-KMT`, KSI metrics (20x only)**

| Class | Before | After |
|---|---|---|
| A | MAY include historical metrics | unchanged |
| B | **MUST** include: 30-day summary and up-to-one-year summary per KSI | **SHOULD**, same two items |
| C | MUST include: 30-day summary, up-to-one-year summary, and "All daily metric data up to the past year (where available)" | MUST, same items. The third item now reads "All daily metric data **(including status of persistent validation)** up to the past year (where available)" |
| D | MUST significantly exceed lower classes, details to be set in the 20x Phase 4 Pilot | unchanged |

A new note says that for initial certification, providers need mechanisms in place and must agree to meet the requirement if the service has not yet operated long enough to have the metrics. "Initial Certification" was added to the rule's terms.

**`FRC-CSX-MOT`, "Metrics Over Time for Key Security Indicators," removed (20x only)**

- It was present from at least the June 21 pre-launch commit through the October 5 release.
- Its requirements were:
  - Class A: MAY supply historical metrics.
  - Class B: SHOULD supply historical metrics.
  - Class C: **MUST** supply historical metrics, including status from persistent validation, over **at least the past 6 months** for all KSIs.
  - Class D: **MUST** supply them over **at least the past 18 months**.
- The rule was deleted, not moved. Nothing in the current file references it.
- Its initial-certification note now lives on `SDR-CSX-KMT`.
- Its Class B level (SHOULD) now matches `SDR-CSX-KMT`'s new Class B level.
- **The 6-month and 18-month minimum lookback periods now appear nowhere.** The remaining depth language is KMT's "up to the past year (where available)."

**`FRD-SNT`:** typo fixed ("understand" to "understood").

## Observations across the four releases

1. **Rev5 Class A is now removed from every Rev5-only subset and Rev5-scope rule.** The July 14 change removed it from `CPO-CSF-CPM`, and September 13 removed it from the CPO Rev5 subset and the `FRC` class-change subset.
2. **The 20x metrics-depth requirement got weaker twice.** Class B went from MUST to SHOULD, and the explicit 6-month and 18-month floors for Classes C and D were deleted. The one-year "where available" language and the Class C daily-data requirement remain.
3. **Validation status is now part of the metrics requirement.** Class C daily data must include the status of persistent validation.
4. **Machine-consumption expectations increased.** `FRC-CSO-JSN` and `CDS-CSO-PUB` now say public JSON must work in a browser-based application. The September 13 structured timeframes point the same way for the rules themselves.
5. **Force semantics were formalized.** For the first time the glossary defines what MUST, SHOULD, and MAY oblige providers to do, including documenting decisions about SHOULD and MAY rules.
